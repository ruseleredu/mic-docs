Nesta aula você entra dentro do firmware enquanto ele roda. O Wokwi tem um servidor GDB: com ele, o VS Code para o ESP32 simulado numa linha, mostra as variáveis e a pilha de chamadas, avança uma instrução por vez, muda um valor na memória e deixa o firmware seguir. É o mesmo GDB que, numa placa real, conversaria com o chip por JTAG.

Objetivos​

  • Configurar o Wokwi for VS Code como alvo de depuração (gdbServerPort, launch.json, extensão C/C++) e conectar o GDB do toolchain do ESP-IDF.
  • Usar breakpoints (de linha, condicionais, de função), passo a passo (step, next, finish, stepi), a pilha de chamadas, os painéis Variables e Watch e o Debug Console (-exec).
  • Ler a memória e o estado do FreeRTOS pelo GDB: a fila de eventos, a task de cada núcleo, a pilha.
  • Depurar um crash antes do reboot e mudar o estado do programa para contorná-lo.
  • Entender o que a otimização tira do depurador.
  • Achar um defeito de corrupção de memória com um watchpoint.

Material​

  • VS Code + PlatformIO + Wokwi for VS Code (com a licença que você já usa) + extensão C/C++ da Microsoft (ms-vscode.cpptools), que é quem fala com o GDB.
  • O GDB do Xtensa. Desde o GCC 12, a Espressif distribui o GDB separado do compilador, e a plataforma espressif32@7.1.0 com framework = espidf já o instala junto do build, no pacote tool-xtensa-esp-elf-gdb (versão 12.1 no Linux e no macOS, 11.2 no Windows). Nada para baixar.
  • O circuito de sempre, com o diagram.json que já passa no wokwi-cli lint (Lab 10).
  • mosquitto_pub/mosquitto_sub via Docker, como nos labs anteriores.
O caminho do GDB na documentação do Wokwi é outro

A documentação do Wokwi para PlatformIO aponta para ~/.platformio/packages/toolchain-xtensa-esp32/bin/xtensa-esp32-elf-gdb. Esse é o toolchain antigo (GCC 8, usado pelo Arduino), que trazia o GDB dentro dele. O nosso firmware usa o toolchain novo (toolchain-xtensa-esp-elf, GCC 15), que não tem GDB: ele está em ~/.platformio/packages/tool-xtensa-esp-elf-gdb/. Confira se a pasta existe:

Terminal (Linux/macOS; no Windows: dir %USERPROFILE%.platformio\packages)
ls ~/.platformio/packages/ | grep gdb
ls ~/.platformio/packages/tool-xtensa-esp-elf-gdb/bin/

1.3 A primeira sessão​

A ordem importa: o simulador abre o servidor, e só então o GDB pode conectar.

  1. pio run (o ELF precisa estar atualizado: o GDB lê as linhas dele, não do seu .c).
  2. F1 → Wokwi: Start Simulator and Wait for Debugger. O simulador abre, mas fica parado.
  3. Abra src/main.c e clique à esquerda do número da linha de void app_main(void): aparece um ponto vermelho (breakpoint).
  4. F5 (com "Wokwi GDB" selecionado). O VS Code conecta, o firmware dá boot e para em app_main.

Repare no painel Call Stack: app_main foi chamada por main_task, que foi chamada por vPortTaskWrapper. É o mecanismo que o Lab 09 descreveu ("quem chama o app_main?"), agora visível. Parte 3 — Memória e FreeRTOS pelo GDB​

O GDB conhece os tipos de tudo o que foi compilado com -g, inclusive as estruturas internas do FreeRTOS. Com um cast, dá para olhar dentro de um QueueHandle_t, que para o seu código é só um ponteiro opaco. Pare em ler_e_publicar() (na segunda leitura do DHT22) e rode no Debug Console:

4.1 nulo: parar dentro do panic​

O panic handler do ESP-IDF só entrega o controle ao depurador sozinho se detectar um depurador JTAG no chip. Com o servidor GDB de um simulador, não conte com isso: ponha você mesmo um breakpoint de função em esp_panic_handler e mande o cmd/falha nulo.

4.2 div0: evitar o crash​

Ponha um breakpoint em media() e mande cmd/falha div0. Olhe os argumentos.

Saída de referência (QEMU)
Thread 2 hit Breakpoint 1, media (soma=1061176952, n=1061175468) at src/falhas.c:38

Lixo de novo, e não é a exceção: o breakpoint caiu na própria instrução entry, antes de a janela de registradores girar (Lab 11, T2). Os argumentos ainda estão em a10/a11 do chamador. Dê um stepi e olhe de novo: agora soma = 1234 e n = 0. Então:

Debug Console
-exec stepi
-exec info args
-exec set var n = 2
-exec info args

Remova o breakpoint e dê Continue. No serial aparece I (...) falhas: media = 617, e o ESP32 não reinicia.

Mude o valor no lugar certo

Se você fizer o set var n = 2 antes do stepi, o GDB escreve no registrador errado, a divisão acontece com n = 0 e o crash vem do mesmo jeito. No Xtensa, só confie nos argumentos depois do entry.

4.3 travar: destravar sem reiniciar​

Mande cmd/falha travar e espere aparecer o task_wdt e a enxurrada de fila cheia. Agora:

  1. Pause (F6). A CPU pode parar dentro de um vetor de interrupção (o tick do FreeRTOS roda 1000 vezes por segundo), e aí o Call Stack fica curto. Não se preocupe.
  2. Ponha um breakpoint na linha while (!liberar) voltas++; e dê Continue: ele para na hora, porque a CPU 1 não sai dali.
  3. Olhe voltas e a fila (-exec print ((Queue_t *) fila)->uxMessagesWaiting).
  4. -exec set var liberar = 1, remova o breakpoint e dê Continue.

A task app sai do laço, processa os 16 eventos que estavam na fila e volta a publicar. O task_wdt para de reclamar. Nada reiniciou.

(b) Por que o set var n = 2 só funciona depois do stepi? (c) O GDB tem um comando return que tira uma função da pilha. Por que este lab usa uma variável liberar em vez de return? Projeto integrador — caça ao defeito com watchpoint​

O filtro.c do template tem um defeito. Com o DHT22 parado em 24,5 °C (o valor inicial do diagrama), o .../dht mostra:

mosquitto_sub .../dht (trecho)
{"grupo":"a","seq":1,"t":24.5,"t_media":24.5,...}
{"grupo":"a","seq":2,"t":24.5,"t_media":24.5,...}
{"grupo":"a","seq":3,"t":24.5,"t_media":24.5,...}
{"grupo":"a","seq":4,"t":24.5,"t_media":24.5,...}
{"grupo":"a","seq":5,"t":24.5,"t_media":12.2,...}
{"grupo":"a","seq":6,"t":24.5,"t_media":12.2,...}

A média de quatro leituras iguais a 24,5 não pode ser 12,2. E nenhuma linha de código faz soma = ... com metade de nada. Alguém está escrevendo onde não devia.

A ferramenta: watchpoint​

Um watchpoint para o programa quando um endereço de memória muda, seja qual for a linha que escreveu. O ESP32 tem dois comparadores de endereço no hardware para isso, e o GDB os usa (hardware watchpoint). Um breakpoint pergunta "quando esta linha roda?"; um watchpoint pergunta "quem mexeu nesta variável?".

Debug Console
-exec watch filtro_dht.soma

(No VS Code também dá para clicar com o botão direito numa variável do painel Variables e escolher Break When Value Changes.)

Requisitos​

  1. Reproduza o sintoma no Wokwi (deixe 6 leituras passarem) e anote o seq em que t_media errou.

  2. Prenda o defeito: reinicie a sessão, pare em app_main, crie o watchpoint em filtro_dht.soma e dê Continue a cada parada. Em cada uma, anote o valor antigo, o novo, a linha e f->pos. Ache a parada em que soma muda numa linha que não deveria escrever nela.

  3. Prove o mecanismo com o GDB:

    Debug Console (parado no filtro_adicionar)
    -exec print *f
    -exec print &f->amostras[4]
    -exec print &f->soma
    -exec ptype filtro_t

  4. Corrija o filtro.c (uma linha) e verifique com o mesmo watchpoint: agora soma só muda nas linhas certas, e o t_media do .../dht fica certo também com temperaturas diferentes (mexa no DHT22 do Wokwi).

  5. Evidências: evidencias/t6-filtro.md com a tabela das paradas (antes e depois da correção), a saída dos comandos do item 3 e a explicação em três frases; evidencias/t6-watchpoint.png com o VS Code parado no watchpoint que entrega o defeito.

Se o watchpoint não funcionar no Wokwi

O watchpoint de hardware depende do servidor GDB do simulador. Se o Wokwi recusar o watch (ou o GDB disser que usou um software watchpoint, que avança instrução por instrução e fica lento demais), use um breakpoint condicional na linha f->amostras[f->pos] = x; com a condição f->pos >= FILTRO_N, e registre no t6-filtro.md qual dos dois caminhos você usou.
