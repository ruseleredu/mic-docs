Laboratório 08

Checklist — Node-RED e SQLite: gravar, consultar e manter​

  • Firmware do Lab 07 publicando em elt73a/lab08/...; banco lab08.sqlite com as tabelas leituras e atuacao criadas em modo Batch (T1)
  • Gravação com INSERT preparado, validação na function e CHECK no banco; ataque de injeção de SQL gravado como texto (T2)
  • Consultas das leituras: resumo por minuto (GROUP BY), falhas na sequência e intervalo real (LAG()) (T3)
  • Consultas da atuação: tempo em cada estado, energia por modo e trocas do aquecedor (LEAD(), LAG()) (T4)
  • Dashboard com histórico vindo do banco, período escolhido por dropdown ($janela) e tabelas de resumo (T5)
  • Manutenção: índice e plano de consulta, resumo por minuto, retenção em transação e VACUUM (T6)
  • Previsões P1–P5 respondidas no README.md
  • Nenhum push --force; cada tarefa num commit Tn:
Pontuação

T1…T6 = 100 pts (esta aula não tem desafios): T1 10 · T2 20 · T3 15 · T4 15 · T5 20 · T6 20. O autograder normaliza para 0–10. Vale o commit Tn: mais recente de cada tarefa.

Nos Labs 06 e 07 o Node-RED só mostrava o presente: a tela do OLED, o estado dos atuadores, os sliders. Bastava fechar o dashboard para tudo sumir. Nesta aula o firmware não muda (é o do Lab 07, só com os tópicos em lab08). Quem trabalha é o Node-RED, que passa a guardar tudo num banco SQLite e a responder perguntas sobre o passado:

  • alguma leitura se perdeu? o ESP32 reiniciou?
  • quanto tempo o controle ficou aquecendo, e quanta energia o aquecedor gastou?
  • como era a temperatura na última hora, mesmo com o dashboard fechado?
  • e o banco: ele cresce para sempre? quanto ocupa? as consultas continuam rápidas?

Objetivos​

  • Criar um esquema com tipos, valores padrão e restrições CHECK, e saber quando usar cada modo do nó sqlite (Via msg.topic, Fixed, Prepared, Batch).
  • Gravar dados vindos do MQTT com INSERT preparado, validando no Node-RED e no banco, e ver na prática por que concatenar SQL é perigoso.
  • Responder perguntas com SQL: GROUP BY, funções de janela LAG() e LEAD(), UNION ALL e médias ponderadas pelo tempo.
  • Montar um dashboard que carrega o histórico do banco, com consulta parametrizada.
  • Manter o banco: índice e EXPLAIN QUERY PLAN, tabela de resumo, retenção dentro de uma transação e VACUUM.

Material​

  • VS Code + PlatformIO + extensão Wokwi (ESP32 simulado), com o circuito do Lab 07.
  • Stack Docker do curso: Node-RED com node-red-node-sqlite e o Dashboard 2.0, já instalados na imagem.
  • O mosquitto_pub via Docker (eclipse-mosquitto:2), como nos labs anteriores.
  • Nenhuma biblioteca nova no firmware.
Onde o banco fica

O SQLite é um arquivo. O banco desta aula é /data/sqlite/lab08.sqlite dentro do container do Node-RED. Como /data é uma pasta montada do seu computador, o arquivo sobrevive a um restart e você pode copiá-lo. Se o Node-RED reclamar failed to open /data/sqlite/..., a pasta sqlite não existe: crie-a (docker exec <container-do-node-red> mkdir -p /data/sqlite) e faça o Deploy de novo.

1.3 Esquema​

Crie um inject "Criar tabelas" (Inject once after 0,5 s) com o SQL abaixo em msg.topic, ligado a um sqlite em modo Batch without response:

msg.topic do inject 'Criar tabelas' (modo Batch)
CREATE TABLE IF NOT EXISTS leituras (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    recebido_em TEXT NOT NULL DEFAULT (strftime('%Y-%m-%d %H:%M:%f', 'now', 'localtime')),
    grupo       TEXT NOT NULL,
    seq         INTEGER,
    t           REAL NOT NULL CHECK (t BETWEEN -40 AND 80),
    h           REAL NOT NULL CHECK (h BETWEEN 0 AND 100),
    uptime_ms   INTEGER,
    intervalo_s REAL,
    origem      TEXT NOT NULL DEFAULT 'esp32' CHECK (origem IN ('esp32', 'manual'))
);

CREATE TABLE IF NOT EXISTS atuacao (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    recebido_em TEXT NOT NULL DEFAULT (strftime('%Y-%m-%d %H:%M:%f', 'now', 'localtime')),
    modo        TEXT NOT NULL CHECK (modo IN ('pot', 'remoto', 'auto')),
    estado      TEXT,
    aq          REAL NOT NULL CHECK (aq BETWEEN 0 AND 100),
    ve          REAL NOT NULL CHECK (ve BETWEEN 0 AND 100),
    aq_duty     INTEGER,
    ve_duty     INTEGER,
    sp          REAL,
    t           REAL
);

Repare no que mudou em relação a uma tabela "solta":

  • NOT NULL e CHECK: o banco recusa uma temperatura de 999 °C ou um modo turbo, mesmo que a validação do Node-RED falhe. É a segunda linha de defesa.
  • DEFAULT (strftime(...)): a hora de chegada é preenchida pelo banco, com milissegundos. 'localtime' usa o fuso do container (variável TZ).
  • IF NOT EXISTS: rodar o inject de novo não apaga nada.

SELECT type, name, sql FROM sqlite_master WHERE name NOT LIKE 'sqlite_%' ORDER BY type DESC, name;
Preveja antes de rodar

// .../dht (ou leitura injetada à mão) -> parâmetros do INSERT preparado.
// Broker público: QUALQUER um pode publicar no seu tópico -> valide antes de gravar.

const num = (v) => typeof v === "number" && isFinite(v);
if (!p || typeof p !== "object" || !num(p.t) || !num(p.h)) {

msg.params = {

A function só confere o formato (são números?). A faixa (−40 a 80 °C, 0 a 100 %) fica com o CHECK do banco. Assim a regra vive num lugar só.

       CASE WHEN seq < anterior THEN 'ESP32 reiniciou'

Parte 4 — Tempo e energia com LEAD​

A tabela atuacao é diferente: cada linha é um evento de mudança, que vale até a próxima. A duração de um estado é o tempo até a linha seguinte, e é isso que a função de janela LEAD() devolve. A última linha ainda está "em andamento", então o LEAD() usa o agora como valor padrão:

Tempo em cada estado (LEAD)
SELECT estado, COUNT(*) AS trocas, ROUND(SUM(dt_s), 1) AS segundos
FROM (SELECT estado, (julianday(LEAD(recebido_em, 1, strftime('%Y-%m-%d %H:%M:%f', 'now', 'localtime'))
                  OVER (ORDER BY id)) - julianday(recebido_em)) * 86400 AS dt_s FROM atuacao)
GROUP BY estado ORDER BY segundos DESC;
Energia do aquecedor por modo (25 W)
SELECT modo, ROUND(SUM(25.0 * aq / 100.0 * dt_s) / 3600.0, 4) AS energia_wh,
       ROUND(SUM(dt_s) / 60.0, 1) AS minutos,
       ROUND(SUM(aq * dt_s) / SUM(dt_s), 1) AS duty_pct
FROM (SELECT modo, aq, (julianday(LEAD(recebido_em, 1, strftime('%Y-%m-%d %H:%M:%f', 'now', 'localtime'))
                  OVER (ORDER BY id)) - julianday(recebido_em)) * 86400 AS dt_s FROM atuacao)
GROUP BY modo;
Trocas do aquecedor no modo auto (LAG)
SELECT COUNT(*) AS trocas_do_aquecedor
FROM (SELECT aq, LAG(aq) OVER (ORDER BY id) AS aq_antes FROM atuacao WHERE modo = 'auto')
WHERE aq <> aq_antes;

energia_wh soma potência × tempo: 25 W × (duty em %) × duração. duty_pct é a média ponderada pelo tempo, diferente da média simples das linhas: um estado que durou 10 minutos pesa mais que um que durou 2 segundos.

5.1 Período e consulta parametrizada​

ui-dropdown "Período" (grupo Histórico, pass-through desligado) com três opções:

RótuloValor
últimos 10 min-10 minutes
última hora-1 hours

O valor é um modificador do strftime() do SQLite: strftime(..., 'now', 'localtime', '-1 hours') é "agora menos uma hora". Um inject (once, 2 s, payload -1 hours) liga no dropdown, para ele já aparecer selecionado, e na function:

function: período -> $janela
// período escolhido -> parâmetro $janela das duas consultas (modificador do strftime)
const ok = ["-10 minutes", "-1 hours", "-24 hours"];
const janela = ok.includes(msg.payload) ? msg.payload : "-1 hours";
flow.set("janela", janela);
return { params: { $janela: janela } };

A function liga em dois sqlite Prepared Statement:

sqlite: histórico T e SP (Prepared)
SELECT recebido_em AS ts, 'T (°C)' AS serie, t AS valor
FROM leituras
WHERE origem = 'esp32' AND recebido_em >= strftime('%Y-%m-%d %H:%M:%f', 'now', 'localtime', $janela)
UNION ALL
SELECT recebido_em, 'SP (°C)', sp
FROM atuacao
WHERE sp IS NOT NULL AND recebido_em >= strftime('%Y-%m-%d %H:%M:%f', 'now', 'localtime', $janela)
ORDER BY ts;

FROM atuacao WHERE recebido_em >= strftime('%Y-%m-%d %H:%M:%f', 'now', 'localtime', $janela)
UNION ALL
SELECT recebido_em, 'Ventilador (%)', ve
FROM atuacao WHERE recebido_em >= strftime('%Y-%m-%d %H:%M:%f', 'now', 'localtime', $janela)
ORDER BY ts;

Projeto integrador — manutenção do banco​

Uma leitura a cada 5 s são 17 280 linhas por dia por grupo. O SQLite aguenta isso com folga, mas um sistema que só cresce um dia fica lento e enche o disco. Um banco de telemetria precisa de três cuidados: índice para as consultas por período, resumo do que é antigo e retenção (apagar o detalhe que já foi resumido).

Requisitos​

  1. Plano de consulta e índice. O dashboard da T5 filtra por recebido_em. Veja como o SQLite executa essa consulta antes e depois do índice:

    inject 'Plano da consulta por período' (sqlite consultas)
    EXPLAIN QUERY PLAN SELECT COUNT(*) AS n, ROUND(AVG(t), 2) AS t_media FROM leituras
    WHERE recebido_em >= strftime('%Y-%m-%d %H:%M:%f', 'now', 'localtime', '-5 minutes');
    inject 'Criar índices e leituras_min' (sqlite Batch, once)
    CREATE INDEX IF NOT EXISTS idx_leituras_recebido ON leituras (recebido_em);
    CREATE INDEX IF NOT EXISTS idx_atuacao_recebido ON atuacao (recebido_em);

    CREATE TABLE IF NOT EXISTS leituras_min (
        minuto  TEXT PRIMARY KEY,      -- 'AAAA-MM-DD HH:MM'
        n       INTEGER NOT NULL,
        t_media REAL, t_min REAL, t_max REAL,
        h_media REAL
    );

    Antes: SCAN leituras (lê a tabela inteira). Depois: SEARCH leituras USING INDEX idx_leituras_recebido (recebido_em>?).

  2. Resumo e retenção numa transação. Um inject "Manutenção" que repete a cada 5 minutos, ligado ao sqlite Batch:

    msg.topic do inject 'Manutenção' (sqlite Batch)
    BEGIN;
    INSERT OR REPLACE INTO leituras_min (minuto, n, t_media, t_min, t_max, h_media)
    SELECT substr(recebido_em, 1, 16), COUNT(*), ROUND(AVG(t), 2), ROUND(MIN(t), 1), ROUND(MAX(t), 1), ROUND(AVG(h), 2)
    FROM leituras
    WHERE origem = 'esp32'
      AND recebido_em < strftime('%Y-%m-%d %H:%M', 'now', 'localtime', '-10 minutes')
    GROUP BY 1;
    DELETE FROM leituras
    WHERE origem = 'esp32'
      AND recebido_em < strftime('%Y-%m-%d %H:%M', 'now', 'localtime', '-10 minutes');
    COMMIT;

    As leituras com mais de 10 minutos viram uma linha por minuto em leituras_min e são apagadas de leituras. Num sistema real a janela seria de dias ('-7 days'); aqui são 10 minutos para você ver o efeito na aula.

  3. Tamanho e histórico longo.

    inject 'Tamanho do banco'
    SELECT p.page_count * s.page_size AS bytes, f.freelist_count AS paginas_livres,
           (SELECT COUNT(*) FROM leituras) AS leituras,
           (SELECT COUNT(*) FROM leituras_min) AS minutos_resumidos
    FROM pragma_page_count() AS p, pragma_page_size() AS s, pragma_freelist_count() AS f;
    inject 'Histórico longo (resumo + recente)'
    SELECT minuto, n, t_media, t_min, t_max FROM leituras_min
    UNION ALL
    SELECT substr(recebido_em, 1, 16), COUNT(*), ROUND(AVG(t), 2), ROUND(MIN(t), 1), ROUND(MAX(t), 1)
    FROM leituras WHERE origem = 'esp32' AND substr(recebido_em, 1, 16) NOT IN (SELECT minuto FROM leituras_min)
    GROUP BY 1
    ORDER BY minuto DESC LIMIT 30;

    O "histórico longo" junta o resumo (minutos antigos) com o detalhe recente agregado na hora: quem consulta não precisa saber onde cada minuto está guardado.

  4. VACUUM. Um inject com VACUUM; no sqlite "consultas". Rode "Tamanho do banco" antes e depois.

Dicas​

  • O corte usa strftime('%Y-%m-%d %H:%M', ...), sem segundos: só minutos completos são resumidos, então um minuto nunca fica metade em leituras_min e metade em leituras.
  • INSERT OR REPLACE com minuto como PRIMARY KEY torna a manutenção idempotente: rodar duas vezes não duplica nada.
  • EXPLAIN QUERY PLAN não executa a consulta: só mostra o plano. Use-o sempre que uma consulta ficar lenta.
  • Depois da manutenção, o período "última hora" do dashboard só mostra a temperatura dos últimos 10 minutos: o detalhe mais antigo foi apagado. Num sistema real, a retenção do detalhe é maior que o maior período do dashboard (ou o dashboard passa a ler leituras_min para os períodos longos).
